title: "Event buses"
description: "Choose a transport by what it does for an instance that was disconnected."
---

Every transport carries the same three events, and the cache configuration does not change between them. Swapping Redis Pub/Sub for NATS JetStream changes one constructor call. See [invalidation](/docs/concepts/invalidation) for what those events are and what a peer does with each one.

What does change is what happens to an instance that was not connected when an event was published.

## Comparison

| Transport | Delivery | What an offline instance gets | Extra infrastructure |
| --- | --- | --- | --- |
| Redis Pub/Sub | At-most-once | Nothing. It misses those events and serves the old value until the TTL expires. | None if Redis is already your L2 |
| NATS Core | At-most-once | Nothing, same as Pub/Sub. | A NATS server |
| RabbitMQ, `durableInvalidationMode` | Durable | Its named queue holds the events and delivers them on reconnect. | A RabbitMQ broker, plus one queue per instance |
| NATS JetStream | Durable | Its durable consumer replays from the last acknowledged message, with redelivery on failure. | A NATS server with JetStream enabled, plus a stream and one consumer per instance |

## Choosing

You already run Redis and a missed invalidation costs you staleness until the TTL expires. Use [Redis Pub/Sub](/docs/guides/buses/redis). It adds no infrastructure.

You want the fastest fanout and accept the same trade. Use [NATS Core](/docs/guides/buses/nats-core).

You cannot miss an invalidation. Use [RabbitMQ](/docs/guides/buses/rabbitmq) in durable mode or [NATS JetStream](/docs/guides/buses/nats-jetstream).

"Cannot miss" is narrower than it sounds. At-most-once loses events during the window an instance is disconnected — a rolling deploy, a pod restart, a network partition, a paused container. The cost is that instance serving the previous value for the remainder of the key's TTL. Ask what that costs you. A stale product description for 60 seconds is staleness. A revoked session, a deleted record, a price that a peer keeps serving after you changed it, or a key whose TTL is measured in hours is a correctness problem, and durable delivery is what fixes it.

## Give every instance a stable identity

Every instance needs a unique value that survives its own restarts. It does two jobs.

The cache stamps it on every event it publishes as `source`, and ignores incoming events whose `source` matches its own, so an instance does not re-apply its own work. In durable mode it also names the RabbitMQ queue or the JetStream consumer that holds events while the instance is down.

Pass it as `source`, and read it from the environment rather than hardcoding it.

| Platform | Value |
| --- | --- |
| Kubernetes | `$HOSTNAME` — the pod name |
| Docker Compose | `web-1`, set per service in the compose file |
| PM2 | `api-${NODE_APP_INSTANCE}` |
| Local development | `dev-local` |

```ts
const cache = new LazyLayersCache({
  l2,
  eventBus,
  source: process.env.INSTANCE_ID,
});
```

If you leave `source` unset, the cache generates a random identifier for the process. Self-filtering still works, but the value changes on every restart, so it is useless for naming a durable queue and hard to read in logs.

<Warning>
Two instances sharing one `INSTANCE_ID` break in two ways at once. Each one treats the other's events as its own and drops them, so neither invalidates. In durable mode they also bind to the same queue or consumer and compete for messages, so each event reaches one of them rather than both.
</Warning>

## Options that apply to every transport

These are cache options, not bus options. They behave the same whichever transport you pass.

<ParamField path="eventBus" type="EventBus">
  The bus instance. Without one, the cache never publishes and never subscribes.
</ParamField>

<ParamField path="source" type="string">
  This instance's identity. Defaults to a random per-process identifier.
</ParamField>

<ParamField path="subscribeToEvents" type="boolean" default="true">
  Subscribe to the bus on construction. Set it to `false` for a process that should publish its own writes but not apply anyone else's, such as a worker with no read path.
</ParamField>

<ParamField path="broadcastSet" type="boolean" default="true">
  Publish a `set` event when a `getOrSet` loader returns a value, so peers write it straight into L1. Set it to `false` for delete-only behaviour, where peers reload each key themselves.
</ParamField>

<ParamField path="broadcastSetMaxBytes" type="number">
  Skip the `set` broadcast when the encoded event exceeds this many bytes. No cap by default. The value is still written to L1 and L2 normally, and the skip emits a `set:broadcast-skipped` event carrying the size.
</ParamField>

<ParamField path="eventDedupeMaxEntries" type="number" default="10000">
  How many recent event IDs to remember so a redelivery is not applied twice. The oldest entries are evicted past this bound.
</ParamField>

<ParamField path="eventDedupeTtlMs" type="number" default="300000">
  How long an event ID stays in that set. Five minutes.
</ParamField>

<ParamField path="resilience.eventBusCircuitBreaker" type="object">
  Opens after `failureThreshold` consecutive publish failures (default `3`) and stays open for `cooldownMs` (default `30000`) before trying one probe publish. While it is open the cache skips publishing and emits `event-bus:publish-skipped`. Local reads and writes are unaffected.
</ParamField>

<Note>
A publish skipped by the circuit breaker never reaches the bus, so the bus retry queue below does not buffer it. The breaker protects the local cache from a broker that is failing every call. The retry queue handles the shorter failures that get through.
</Note>

## The retry queue

Every transport accepts the same `retryQueue` options.

```ts
retryQueue: { enabled: true, maxSize: 10_000 },
```

<ParamField path="retryQueue.enabled" type="boolean" default="true">
  Buffer an event in memory when publishing it fails, and flush the buffer ahead of the next successful publish.
</ParamField>

<ParamField path="retryQueue.maxSize" type="number" default="10000">
  Cap on buffered events. Past it, the oldest event drops with a warning.
</ParamField>

The bound is deliberate. During a long broker outage the queue would otherwise grow for as long as your instance keeps writing, and hold every buffered value in memory until the process runs out of heap. Shedding the oldest invalidations costs you staleness on those keys. Growing without a limit costs you the process, and with it every entry in L1.

The queue lives in the instance's memory, so a restart discards it. It covers a broker blip, not a broker outage that outlasts your deploy.

## Check the bus before you serve traffic

Every bus in the package exposes `healthCheck()`, which returns an object with an `ok` flag and transport-specific fields rather than throwing.

```ts
import { NatsEventBus } from 'lazy-layers-cache';

const eventBus = new NatsEventBus({
  mode: 'jetstream',
  connectionOptions: { servers: process.env.NATS_URL },
  subject: 'app.invalidate',
  jetstream: { durableName: process.env.INSTANCE_ID },
});

const health = await eventBus.healthCheck();

if (!health.ok) {
  logger.error({ health }, 'cache event bus unhealthy');
  process.exit(1);
}

app.listen(3000);
```

The check connects, and on the transports that need it, creates the stream and consumer or asserts the exchange. A wrong URL, missing credentials, a JetStream mode with no `durableName`, or a broker that is not up yet all surface here.

That ordering is the point. Without the check, a bus that never connects fails silently — the cache keeps serving reads from its own L1 and simply never hears about anyone else's writes. You get stale data instead of an error. Exiting before `listen` turns a configuration mistake into a failed startup that your orchestrator will retry or roll back.

## Ordering

How many handlers run at once depends on the transport, and there is no single default.

| Transport | Concurrency | Controlled by |
| --- | --- | --- |
| Redis Pub/Sub | 1 | `handlerConcurrency` |
| NATS Core and JetStream | 1 | The message loop awaits each handler |
| RabbitMQ | Unbounded by default | `prefetch` |

Redis and NATS apply events one at a time, which preserves approximate order. RabbitMQ does not await the handler, so messages are processed as fast as they arrive unless you set `prefetch`. Set it if you want that bounded.

Order across the bus is never guaranteed on any transport. Two instances writing the same key concurrently can have their events arrive anywhere relative to each other, and a durable transport that redelivers can replay an event after a newer one. Per-key generations are what make that safe. See [event ordering](/docs/architecture/event-ordering).
